# SPEC-012 — Staged Semantic Compilation

## Status

Ready for implementation.

## Phase

Phase II — realistic-source semantic reliability.

## Primary Question

> Does separating canonical entity/symbol discovery from semantic linking materially improve referential integrity and semantic relationship precision on the exact frozen realistic quantum source that repeatedly broke one-pass extraction in SPEC-011?

## Evidence That Earned This Experiment

SPEC-011 exposed the same 5,965-word / 39,735-character quantum source to the current one-pass extraction architecture twice.

Both attempts failed closed because generated relationships referenced entities absent from the generated entity inventory:

```text
Attempt 1
relationship → measurement
               ↑
          entity absent

Attempt 2
relationship → quantum-theory
               ↑
          entity absent
```

The second rejected proposal nevertheless contained:

```text
27 entities
11 relationships
9 claims
0 propositions
20/20 exact unique evidence spans
```

Independent semantic review also found materially misleading but mechanically grounded edges.

Therefore the observed problem has at least two dimensions:

```text
1. REFERENTIAL CONSISTENCY
   entity inventory ↔ semantic endpoints

2. SEMANTIC PRECISION
   does the source actually support this predicate
   between these exact endpoints?
```

SPEC-012 tests one architectural hypothesis generated by that evidence. It must not assume the hypothesis is correct.

## Architectural Hypothesis

The current one-pass contract asks one probabilistic generation to simultaneously discover the symbol space and link propositions inside it.

Hypothesis:

```text
SOURCE
  ↓
PASS 1 — SYMBOL DISCOVERY
  ↓
canonical entity inventory
  ↓
freeze symbol table
  ↓
PASS 2 — SEMANTIC LINKING
  ↓
relationships / claims / propositions
restricted to known symbols
  ↓
existing trusted validation
  ↓
KnowledgeModel
```

may outperform:

```text
SOURCE
  ↓
ONE-PASS EXTRACTION
  ↓
entities + relationships + claims + propositions
simultaneously
  ↓
existing trusted validation
```

The LLM should be treated as a probabilistic semantic proposal mechanism inside a deterministic compiler boundary, not as the trusted compiler itself.

## Experimental Design

This is an architecture comparison experiment.

### Frozen benchmark

Use exactly the SPEC-011 source:

- Wikipedia — `Introduction to quantum mechanics`
- revision `1359567407`
- 5,965 words
- 39,735 characters
- source metadata already committed by SPEC-011

Do not change the source, shorten it, segment it, enrich it, or substitute another quantum article for the primary comparison.

### Control

The accepted control is the **existing SPEC-011 one-pass result**, including both preserved failed attempts.

Do not spend a new live call rerunning the one-pass control unless the experiment cannot be compared fairly without it and explicit owner approval is obtained first.

Primary control evidence:

```text
SPEC-011 attempt 1 → dangling endpoint: measurement
SPEC-011 attempt 2 → dangling endpoint: quantum-theory
```

Use the preserved second rejected proposal for detailed semantic comparison.

### Experiment

Implement a bounded two-pass staged extractor for the same source.

```text
PASS 1
symbol discovery

PASS 2
semantic linking against frozen symbols
```

No third semantic pass is allowed in the primary experiment.

No automatic semantic retry is allowed.

If either pass fails, preserve the failure and stop unless the SPEC explicitly permits continuation.

## Pass 1 — Symbol Discovery

### Purpose

Construct the canonical entity inventory that later semantic linking is allowed to reference.

Pass 1 should answer approximately:

> **What semantically meaningful things does this source establish that later relationships, claims, or propositions may refer to?**

### Output

Use the existing canonical `Entity` model wherever possible.

Do not introduce a parallel ontology if the existing entity model is sufficient.

The output should be a deterministic, validated symbol table containing at least:

```text
entity ID
canonical name
entity type
description if supported/required
aliases if supported by current model
```

Trusted code should own final stable IDs and ordering.

### Source grounding

Entity discovery itself does not need to invent a new evidence model merely for this experiment.

If the existing entity model does not carry evidence, do not add entity-level SourceSpan fields speculatively.

However, the symbol-discovery prompt must remain source-bounded and must not supplement the inventory from general quantum knowledge.

### Completeness vs precision

Do not ask Pass 1 to enumerate every noun phrase.

Prefer entities that are semantically useful as later proposition endpoints.

A smaller coherent symbol table is acceptable.

The experiment is precision-first.

### Normalization

Pass 1 should explicitly reduce obvious alias fragmentation where safe, for example where the source clearly uses multiple surface forms for the same concept.

Do not merge distinct concepts merely because they are lexically similar.

Record symbol-table diagnostics such as:

```text
raw nominations
accepted symbols
rejected nominations if applicable
alias normalizations
entity types
```

## Frozen Symbol Table

After Pass 1 validation:

```text
symbol table = immutable input to Pass 2
```

Pass 2 must not create new entities.

This is the core experimental variable.

If Pass 2 needs a concept absent from the symbol table, it must:

- omit the semantic item; or
- record a structured missing-symbol diagnostic;

but it must **not** silently mint a new entity.

Do not automatically run Pass 1 again.

## Pass 2 — Semantic Linking

### Purpose

Extract source-supported:

```text
relationships
claims
propositions
```

using only the frozen Pass-1 entity inventory.

### Prompt boundary

Pass 2 receives:

- the exact same full source;
- the frozen symbol table;
- the existing canonical relationship grammar;
- the existing proposition grammar;
- the existing grounding/provenance rules.

It should be explicitly instructed that all semantic endpoints/roles must reference provided symbol IDs.

Prefer provider structured output that constrains endpoint fields to known symbol IDs if feasible without creating an enormous brittle schema.

If exact enum restriction is impractical at this symbol count, trusted post-generation validation must still reject any unknown IDs.

### Existing semantics remain authoritative

Do not change the canonical 20 relationship predicates.

Do not add quantum-specific predicates.

Do not expand SPEC-010 proposition types/operators/roles unless the staged experiment is otherwise impossible; if so, stop and report rather than silently broadening scope.

### Grounding

All current SOURCE evidence requirements remain unchanged:

- exact source quotes;
- deterministic quote-to-SourceSpan resolution;
- missing/ambiguous evidence fails closed;
- inferred items cannot carry source evidence;
- no external enrichment.

## KnowledgeModel Assembly

Trusted code combines:

```text
Pass-1 entities
+
Pass-2 validated relationships
+
Pass-2 validated claims
+
Pass-2 validated propositions
```

into the existing `KnowledgeModel`.

Do not introduce a new canonical semantic IR solely for staged compilation.

Existing downstream consumers should receive an ordinary valid `KnowledgeModel`.

## Scope Boundary

SPEC-012 is **not** a generalized ingestion/chunking architecture.

Do not implement:

- source segmentation;
- map/reduce extraction;
- embeddings;
- vector search;
- retrieval;
- multi-document entity resolution;
- persistent global symbol database;
- ontology service;
- graph database;
- recursive semantic passes;
- self-correction loops;
- automatic repair;
- critique/rewrite agent loops.

The benchmark fit in the provider context window during SPEC-011. Keep the full-source comparison intact.

## Fair Comparison Requirements

Hold constant as much as possible:

```text
source revision

provider
model family/version
canonical entity types
20 relationship predicates
proposition vocabulary
evidence rules
validation rules
no enrichment
store=False
SDK retries disabled
```

The unavoidable experimental difference is that staged compilation uses two prompts/calls rather than one and Pass 2 receives a frozen symbol table.

Document any additional unavoidable prompt differences.

Do not tune prompts after seeing the live staged output during the primary run.

## Live Call Budget

Primary staged experiment requires exactly:

```text
Call 1 — symbol discovery
Call 2 — semantic linking
```

No hidden retries.

No semantic retry without explicit owner approval.

If Pass 1 fails validation, do not make Call 2.

If Pass 2 fails, preserve it as the staged result.

Before transmitting the public benchmark source to the provider, follow the repository's current owner-approval rule for live calls.

## Evaluation Framework

Evaluate the control and staged experiment across **three independent layers**.

## Layer 1 — Structural Validity

Measure at least:

```text
valid entity inventory
dangling relationship endpoints
dangling proposition role bindings
unknown claim references if applicable
duplicate/alias entity identities
schema violations
symbol-table violations
KnowledgeModel round-trip
```

### Primary structural hypothesis

The staged architecture should eliminate the specific class of dangling references seen in SPEC-011 by construction.

But this alone is insufficient for acceptance.

## Layer 2 — Grounding Validity

Measure:

```text
SOURCE semantic item count
INFERRED semantic item count
exact evidence resolution rate
unique evidence rate
missing quote failures
ambiguous quote failures
SOURCE/INFERRED invariant violations
```

Do not weaken grounding relative to SPEC-011.

## Layer 3 — Semantic Validity

This is the decisive layer.

Independently inspect whether each accepted relationship/proposition is actually supported by the source with the asserted predicate and endpoints.

Classify accepted semantic items using a small review vocabulary such as:

```text
SUPPORTED
IMPRECISE_ENDPOINT
WRONG_PREDICATE
REVERSED_DIRECTION
OVERSTATED_CAUSALITY
UNSUPPORTED
LOSSY_BINARY_FORM
OTHER
```

Exact labels may be refined before live evaluation, but must be fixed before seeing staged results.

### Independent review principle

Do not ask the same generating call to judge its own semantic correctness.

Repository/human semantic review remains independent from generation.

A deterministic/manual review artifact is acceptable for this benchmark.

If an LLM-assisted independent reviewer is proposed, that would add another live experimental variable and requires explicit owner approval; do not assume it.

## Precision-First Comparison

Do not reward the staged architecture merely for producing more semantic items.

Report at least:

```text
accepted semantic items
semantically supported items
semantic precision = supported / reviewed accepted items
structural rejection count
grounding rejection count
```

Treat precision as more important than recall/volume for this experiment.

A result like:

```text
18 entities
8 excellent relationships
```

may be preferable to:

```text
40 entities
35 questionable relationships
```

Do not invent a universal production-quality threshold from this single benchmark.

## Control Semantic Baseline

Use the preserved SPEC-011 second proposal as the one-pass semantic baseline.

Its known review defects include at least:

```text
quantum mechanics → CAUSES → molecules
energy quanta → CAUSES → black-body radiation
wave-function collapse self-loop / lost measurement-state semantics
mismatched IS_A semantics around QFT/QED
tunneling endpoint targeting electron rather than electron penetration
```

Do not modify the control artifact.

Map the existing SPEC-011 repository review into the SPEC-012 semantic-review categories where possible.

## Staged Result Outcomes

Record one of:

```text
STAGED_BETTER
NO_MEANINGFUL_IMPROVEMENT
STAGED_WORSE
MIXED
INCONCLUSIVE
```

The verdict must consider all three layers, especially semantic precision.

Examples:

### `STAGED_BETTER`

Appropriate when staged compilation materially improves referential integrity **and** semantic precision without weakening grounding.

### `NO_MEANINGFUL_IMPROVEMENT`

Appropriate if dangling references disappear but semantic precision remains comparable to the weak control.

### `STAGED_WORSE`

Appropriate if staging reduces useful semantic coverage or introduces worse semantic errors without compensating trust gains.

### `MIXED`

Appropriate when structural reliability improves but semantic quality trades off materially against coverage or another important dimension.

### `INCONCLUSIVE`

Use only when provider/operational failure prevents a fair comparison.

## Downstream Gate

If the staged result produces a valid parent `KnowledgeModel`, run existing downstream machinery **only as a diagnostic**, not as the primary acceptance criterion:

```text
StructureDetector
RepresentationBuilder
layout
```

Do not perform a child semantic-resolution live call in SPEC-012.

Why:

SPEC-012 isolates extraction architecture. A child call would introduce another variable and additional cost before parent semantic quality is accepted.

A valid parent may be rendered locally for owner/repository inspection if useful.

Do not interpret attractive visualization as evidence of semantic correctness.

## Parent Representation Diagnostic

If a trusted staged parent exists:

- generate structures;
- generate representations;
- record counts/salience/layout diagnostics;
- provide a local viewer command if existing infrastructure supports it;
- label the viewer as a diagnostic artifact pending semantic review.

If no trusted parent exists, do not render the rejected proposal.

## Cost / Complexity Accounting

Staging spends more provider tokens/calls by design.

Report:

```text
Pass-1 input/output/total tokens
Pass-2 input/output/total tokens
combined staged usage
available one-pass usage from SPEC-011
runtime per pass
combined runtime
authoritative monetary cost if available
prompt sizes
symbol-table size
new code/dependency complexity
```

The experiment should answer not only whether staging is better, but whether the improvement appears worth its added complexity/cost.

Do not fabricate monetary estimates if authoritative pricing/charge data is unavailable under current project convention.

## Determinism

Provider outputs are not expected to be deterministic.

Trusted processing after each provider response must be deterministic:

```text
ID assignment
symbol ordering
validation
evidence resolution
KnowledgeModel assembly
evaluation artifact generation
```

Where possible, preserve raw/rejected provider proposals so trusted processing can be reproduced offline.

## Failure Preservation

Preserve:

- Pass-1 raw/normalized proposal if rejected;
- Pass-2 raw/normalized proposal if rejected;
- request IDs;
- token usage;
- runtime;
- exact validation failure;
- missing-symbol diagnostics;
- run history.

Do not repair rejected proposals before evaluation.
